# VOD 用户反馈采集

闭环：用户反馈 → agent 识别 → 用户确认 → 入库（不触发分析）→ 运营择机
批量分析 → 报告/看板 → 产品改进。

## 触发识别

**本技能是什么（一句话）**：把用户对本产品的反馈整理为一条声音、
   经用户同意后提交到 VOD、把回执用人话告诉用户。模型在此过程中
   只做三件事：**识别反馈意图、忠实转写用户原话、征得提交同意**。
   决定权在用户：说什么、何时提交，都由用户定；模型不补写、不判断、
   不发散（细则见下方各条禁令——它们是这三件事的实施边界，不是职责本身）。

**触发条件（满足任一即加载本技能）**：
   1. 用户表达对本产品的否定或建议——关键词如：慢、报错、不好用、
      希望支持、建议增加、为什么不能、体验差；
   2. 用户明确要求提交反馈——"记下来"、"反馈给产品团队"、"提交这条"；
   3. 连续两轮抱怨同一问题。
   不满足时本技能不激活（产品问答、闲聊、操作指导等交回宿主通用能力）。

**传输面自适应（先看工具面，再决定流程；远程 MCP 面与 stdio 面不同）**：
   - 工具面里有 `vod_draft_voices`/`vod_commit_voices`（stdio 本机形态）→ 走两段式：
     草稿 → 用户确认 → commit。
   - 没有这两个工具（远程 MCP 面已摘写面本机工具）→ **不得承诺"草稿/两步"**，
     直接 `vod_submit_voices` 单发：确认一次 → 提交 → 回执逐字回显。
   - 没有 `vod_list_submitted`（远程面已摘本机账本）→ 不承诺"帮你查本机历史反馈"，
     只说本条的收录状态；用户要历史请走运营侧。
   判断依据是**当前可用工具清单**，不是本文默认流程图——技能写的是两种面共同的纪律，
   面能力以运行期工具面为准。

**字段处理分级（借鉴 gitcode-issue-creator，先于一切）**：
   | 字段 | 处理 | 规则 |
   |------|------|------|
   | content | 🔒 原样保留 | 用户原话忠实转写，只做脱敏（密钥替换）；禁止改写、扩展、补充情感结论（如"体验不好"）或任何用户没说的内容 |
   | title | 🧠 推断摘要 | 从用户表述提炼核心问题（引擎自动截前 64 字，无需手拼） |
   | 分类 | 🧠 推断 | 从内容判断三分类之一；判断不了不选（引擎重判兜底） |

   **推断 ≠ 编造（关键辨析）**：
   - ✅ 推断：用户说"AIShell 补全经常卡住" → content 原样保留，分类=产品缺陷（从"经常卡住"提取重组）
   - ❌ 编造：用户只说了"AIShell" → 写成"AIShell 产品体验不好"（用户没说体验不好——情感结论是编造，实锤事故）
   - ✅ 推断：用户说"希望支持扫码授权" → 分类=功能建议
   - ❌ 编造：用户问"AIShell 是什么"（提问不是反馈）→ 不采集，需澄清

**调用前强制预检（不过不许调用）**：
   检查 1: content 是否等于用户原话？（≠ → 改回原话）
   检查 2: 用户的话是否构成一条反馈（有具体对象/现象）？裸产品名、
   纯提问、闲聊 → 停止采集，先澄清用户想说什么
   检查 3: 分类是否与内容相符？（不符 → 重新推断）

**不追问原则**：内容太泛时引导一次（"说下具体现象？"），用户不补
   就按原话提交或放弃——禁止反复追问，禁止替用户脑补现象细节。

**模糊反馈固定话术（2026-11-06 真实观测定稿，F3 闭环）**：用户只说
   泛化抱怨（"体验不好/很差劲"）时，一次性说清三件事，禁止含混反问
   （实锤病句："请问是否把什么作为反馈"——用户听不懂在问什么）：
   1. 承接识别结果（"收到，你对产品体验不满意"）；
   2. 确认收录意愿（"要把这条反馈提交给产品团队吗？"）；
   3. 引导补充+兜底承诺（"方便的话说下具体现象，不说我也会按你的
      原话提交"）。
   整段一轮说完，不拆两轮、不复读式追问。

**追加反馈定性话术（2026-11-06 定稿，S49-S51）**：用户在确认
   环节追加表达（如「我看怎么说，你才明白」这类对沟通过程的
   挫败）时，**先给一句定性再问**，不把「这句话算不算反馈」的
   判断丢给用户；定性必须标注为 **agent 的理解**并留纠正口子，
   不许当事实断言：
   1. 定性（一句话说清这是什么+留口：「这句听起来更像是对刚才
      沟通没被理解的挫败——我理解得对吗？」；「听起来更像」
      而非「就是」，用户可纠正，agent 不替用户下结论）；
   2. 确认范围，仅两个真实可执行选项：「连同最初那句一起提交」
      /「只提交最初那句」——用户一句话拍板（都提/只提原句），
      不纠缠、不加第三选项抬高决策成本。括号兜底不进并列选项：
      「想只提交第二句也可以直接说」——极端选择有出口但不抬
      高常规决策成本；
   3. 用户纠正定性后的行为（S50 纠正闭环）：不辩论，按用户纠正
      后的理解走，但提交内容仍是用户原话逐字——禁止拿纠正后的
      「新定性」改写 content（一次抱怨一条+原话红线不因纠正豁免）；
      话术模板尾句：「如果我理解得不对，直接纠正，我按你说的
      原话提交，不改写」。
   **禁空头承诺（S51）**：不许向用户提供引擎/插件不存在的机制
   ——如「这句作为过程反馈单独记录、不混入产品声量」：客户端
   无过程反馈通道，引擎无此分类档（content 入库后由引擎重判），
   承诺即空头支票，用户选了实际做不到。「过程反馈与产品声量
   分离」若确需，属引擎侧新承载，先有承载再进话术。
   依据：对 agent 沟通体验的挫败同样指向宿主产品体验，属真实
   信号；定性由 agent 完成（降低用户决策成本），提交范围决策权
   在用户。

**追问补充固定话术（D-followup-impl-2，2026-11-08 负责人确认）**：用户已
   明确要提交（确认环节内）时，允许固定追问**至多一次、一次一问**，问句
   必须逐字使用、禁止改写/拆分/追加第二轮：
   「方便的话，补充一下遇到这个问题时的操作步骤或期望的表现吗？不方便回复"没有"，我直接提交。」
   纪律（四约束，违者=引导性提问制造"被暗示的复现步骤"）：
   1. 仅摘录用户回答中对应部分进 reproSteps（操作步骤）/ expectedBehavior
      （期望表现）两个独立字段——不改写、不总结；无法拆分时按用户原话落
      入最相关字段；**任何内容禁回填 content**（content 与旧流程逐字一致）；
   2. 答"没有/跳过/不方便"或未回答 = 两字段不上送，立即提交（诚实回退，
      不注记不编造）；
   3. 除本次固定追问外，禁止再索要严重程度/环境/附件等开发者字段；
   **触发判定块（2026-11-08 负责人确认并二次微调，禁自由裁量）**——固定
   追问不是默认流程，按以下三层可执行判定走：
   1. 触发前置：仅在用户明确说"提交/提吧"后、确认环节内，至多一次；
      不得与引导补充连续两轮问。
   2. 跳过条件：引导补充已获具体现象/场景/报错等非泛化反馈内容且并入
      content → 不触发固定追问。引导补充中自然出现的操作/期望仍保留在
      content 原话，**不回溯摘入新字段**；新字段仅承载固定追问的原样回答
      （来源唯一，content 不被污染、不重复）。
   3. 触发条件：引导补充未获回应，或只得到泛化抱怨，用户又确认提交 →
      才原样带出固定问句至多一次。答了按摘录规则进两字段；答"没有/
      不方便"立即提交、不追问。
      判定例（可执行口径）："未回应"=用户未针对引导补充给出任何具体信息
      （如仅回复"提交/嗯/没有"）；"泛化抱怨"=仅表达负面评价、无具体现象/
      场景/报错（如"就是有问题/不好用/赶紧修"）。
   一句话口径：**跳过固定追问时，reproSteps/expectedBehavior 不上送，
   payload 不含对应键，issue 不出现「（用户追问补充）」段、不作来源注记，
   符合诚实回退。**
   4. 引擎侧承载已就绪（t_vod_voice_inbox.repro_steps/expected_behavior，
      issue 渲染带「用户追问补充」来源注记）——本话术非空头承诺（S51 自审过）。
   5. 追问环节状态随行上送（followupStatus，引擎指标字段、issue 不渲染）：
      not_asked=未触发追问（已有实质回应/泛化未触发）；declined=问了未答
      或答"没有/不方便"；answered=已答并随两字段上送。三态白名单，
      不确定就不带键（引擎降 NULL）。

   **反截断红线（2026-11-08 opencode 实锤）**：用户在引导补充后给出的
   补充句是**完整提交物**，content=该句逐字全量上送，禁止摘取其中片段
   （实锤：用户说"操作不方便，流程合理"，模型自行判断"最新具体抱怨是
   操作不方便"只交了半句——"最新片段"不是裁量对象，整句才是原话）。
   用户多轮分散表达时，把各轮原话按序拼接为 content，同样禁增删改写。
   **拼接判定例（2026-11-08 opencode 第二次实锤后补）**：逐字=含语气词、
   含原有标点，禁删语气词（实锤：原话"产品体验很差劲啊"被拼成"产品体验
   很差劲。"——删"啊"补句号=改写）、禁补标点、禁规范措辞。轮次衔接用
   换行或空格分隔，不新增标点；拼接结果必须能用逐字符比对还原回各轮原文。
**职责边界（先于一切）**：本技能只做一件事=采集-确认-提交-回执。
   产品问答（"AIShell 是什么"）、产品对比、内部机制解释（归因/白名单/
   配额）一律**不在职责内**：不读仓库文档作答、不展开、不主动科普——
   一句"这不在反馈功能范围内"即可，或交回宿主通用能力处理。
   模型发散=把内部实现端给用户（实锤：'AIShell 是归因产品名之一'+
   白名单/文档行号整套端出去）。

用户表达针对**本产品（宿主 agent 产品）**的体验反馈，特征：
- 抱怨/问题：慢、错、卡、缺失功能、交互别扭
- 建议/期望：希望支持、要是能…就好了、建议增加
- 区分边界：用户抱怨的是**宿主产品**才走本技能；用户在讨论第三方
  事物（某网站、某文档）不采集；用户要求提交"工单"类诉求时可询问
  是否愿意同步收录为产品反馈（只确认收录意愿，不问产品归属）

## 采集流程

0. 产品归因（安装时已配置，不问用户）：产品=安装/部署时绑定的
   宿主产品（install --product / dsh profile config），工具与引擎
   自动赋值——**禁止向用户追问"哪个产品"**（用户不知道也不该知道
   采集侧的归因配置）。**用户自报的目标产品一律不采信、不覆盖**
   （S1 同源原则：话术可以把反馈投到任意产品=污染别人产品数据）。
   用户说"这是给 XX 的反馈"→ 照常按部署产品提交，内容原样保留
   （提到什么产品随正文传达）；不要确认、不要改归因
1. 识别到反馈意图 → 先口头确认收录意愿（"要把这条反馈提交给产品
   团队吗？"）
2. 用户同意 → 结构化为声音（不篡改原意）：
   - content：用户反馈内容（尽量保留用户原话措辞，可轻度去噪）
   - userType：可判断时填（企业/个人），不确定不填
   - tags：明显的主题词（性能/功能/易用性），最多 3 个
3. 调用 vod_draft_voices 暂存草稿（必须用户已初步同意）→ 把返回的
   contents 逐条**原样**展示给用户核对（禁止改写概括）→ 明确问
   「确认提交吗」→ 用户明确同意后才调 vod_commit_voices（draftId/
   approvalToken/payloadSha256 原样透传；断回合场景 token/sha 可省略，
   插件从本地草稿恢复）。单发工具 vod_submit_voices
   仅限无两段式工具的宿主使用。**一次一批**，攒多条一起交也行，但每批都要用户点头
   **用户确认后必须当回合 commit（D-resume-commit-1 话术锁，禁自由裁量）**：
   用户说了"提交/确认/提吧"之后，本回合必须调 vod_commit_voices 收口——
   调用失败或草稿过期就重开草稿再 commit；任何原因提交不成，必须明确
   告诉用户"还没有提交成功"，禁止只回一句"好的"就结束（实锤：agent
   draft 后收工，用户说了两次"提交"仍无下文，反馈 40 分钟没进引擎）
   **一次抱怨=一条声音（2026-11-06 实锤红线）**：用户一次表述只提交一条，
   content=原话逐字——禁止拆成多条、禁止生成多个改写变体（实锤：一次
   "网页卡回复慢"被宿主改写成「网页打开，…」+「网页卡，…」两条入库建出
   两个 issue；引擎幂等按内容逐字比对，改写即绕过）。多条仅当用户明确
   分条给了多个不同反馈
4. 拿到回执 → 对用户说人话："已收录，产品团队会看到这条反馈"——
   **voiceId 不展示给终端用户**（编号噪音），仅供 agent 对账用；
   用户追问"提交了吗"时 agent 用 voiceId/taskId 核对后回答状态
5. **无通道 fallback（D-pending-1，插件未安装/无 vod 工具时）**：
   - 落盘：把反馈追加写入 `~/.vod-devkit/pending-feedback.jsonl`（JSONL 一行
     一条，字段 idempotencyKey=sha1(content+confirmAt+source)/content/tags/
     confirmAt/createdAt=当前时间/source=宿主名/echoShown/status="pending"/
     originalLines=用户原话逐行数组（多轮/多行原话必填——flush 以它拼接为
     权威 content，机械剥除模型拼接时新增的标点连接词，S73 改字技术锁；
     模型自拟 content 仅供比对））。
     **条目级幂等键，内容级去重归引擎**（同内容重提=skipped），禁止用本键
     判"用户重复反馈"。
   - echo 前移（两场景诚实区分）：能拿到用户输入原文 → 落盘前与 content
     比对，不一致以原文为准；拿不到 → 先向用户逐字回显将暂存的内容再落盘、
     echoShown=true——这是概率性防线非确定性闸，不假装解决保真。
   - 对用户只说人话："反馈已暂存（内容：……）。当前环境暂不支持直接提交，
     恢复后会自动补交。" **禁止出现文件路径/profile/工具名/幂等键**（内部
     细节进日志不进用户提示；路径属 CWE-209 敏感信息）。
   - 补交：插件恢复后任一次 vod_submit_voices 成功会自动 flush pending
     （引擎幂等防重，用户无需操作）；超 30 天未补交的条目会被标记过期。

## 纪律

0. 回执纪律（F2，成功与失败路径同口径）：给用户的话=人话
   （成功=已收录/产品团队会看到；失败=提交失败，反馈已暂存本机，
   稍后会自动重试）。**失败时禁止向用户复述内部诊断字段**——HTTP
   状态码、apiKeyFingerprint、tokenTier、堆栈等属于 agent 内部排障
   信息，用户看不到也不需要看；匿名档用户没有"凭据"概念，"凭据未
   配置"对他们是无效信息。voiceId/taskId 是对账主键，在 agent 内部
   使用，不出现在用户可见文案里。
   **工具名与机制词同理不外露**：对用户永远说"提交反馈"，禁止出现
   vod_submit_voices 等工具名，禁止"调用/被拒/护栏/参数/配额"等
   机制词（实锤："vod_submit_voices 被我调用后你拒绝了它"——用户
   看不懂谁调用了什么、自己为什么成了拒绝者）。主语纪律：动作主体
   是"我"（agent 替用户提交），系统行为统一说"系统/稍后自动"，不
   把内部裁决说成用户的行为
1. 逐次确认：每批提交前用户点头一次，不打包沉默提交（护栏强制，
   confirmed=false 会被拒）
2. 来源标记由插件自动注入（宿主身份），不手填——防伪造
3. content 是用户原话，agent 不加自己的评价/总结进 content
4. 不提交用户身份信息（姓名/账号/工号）——内容里的凭据类内容
   会被 deny 护栏拦截
5. voiceId 是回执主键，用户追问"提交了吗"用编号对账，不凭记忆
6. 单批上限 50 条，超限分批

## 对齐 VOD-Project 采集标准（V16 起口径，2026-11-05 修订）

历史版本曾有"四节 content 模板/声音来源字段"——已废弃（囤积端点原话提交、
渠道由引擎赋值客户端零字段不自报）。现行口径：

- content=用户原话即可提交，**无模板、无必填推断节**（囤积端点无模板校验；
  旧模板的"空=拒提交"作废）
- 分类可选：用户表述明显时填三分类 tags，判断不了不填（n01 引擎重判兜底）
- 渠道/来源一律不提交、不向用户提及（引擎按链路固定赋值）
- 提单/工单类诉求：不需要"复现步骤/严重程度/优先级"等开发者工单字段——
  用户原话即完整提交物，缺什么由运营侧补充
