# VOD 用户反馈采集

闭环：用户反馈 → agent 识别 → 用户确认 → 入库（不触发分析）→ 运营择机
批量分析 → 报告/看板 → 产品改进。

## 触发识别

**本技能是什么（一句话）**：把用户对本产品的反馈整理为一条声音、
   经用户同意后提交到 VOD、把回执用人话告诉用户。模型在此过程中
   只做三件事：**识别反馈意图、忠实转写用户原话、征得提交同意**。
   决定权在用户：说什么、何时提交，都由用户定；模型不补写、不判断、
   不发散（细则见下方各条禁令——它们是这三件事的实施边界，不是职责本身）。

**触发条件（满足任一即加载本技能）**：
   1. 用户表达对本产品的否定或建议——关键词如：慢、报错、不好用、
      希望支持、建议增加、为什么不能、体验差；
   2. 用户明确要求提交反馈——"记下来"、"反馈给产品团队"、"提交这条"；
   3. 连续两轮抱怨同一问题。
   不满足时本技能不激活（产品问答、闲聊、操作指导等交回宿主通用能力）。

**字段处理分级（借鉴 gitcode-issue-creator，先于一切）**：
   | 字段 | 处理 | 规则 |
   |------|------|------|
   | content | 🔒 原样保留 | 用户原话忠实转写，只做脱敏（密钥替换）；禁止改写、扩展、补充情感结论（如"体验不好"）或任何用户没说的内容 |
   | title | 🧠 推断摘要 | 从用户表述提炼核心问题（引擎自动截前 64 字，无需手拼） |
   | 分类 | 🧠 推断 | 从内容判断三分类之一；判断不了不选（引擎重判兜底） |

   **推断 ≠ 编造（关键辨析）**：
   - ✅ 推断：用户说"AIShell 补全经常卡住" → content 原样保留，分类=产品缺陷（从"经常卡住"提取重组）
   - ❌ 编造：用户只说了"AIShell" → 写成"AIShell 产品体验不好"（用户没说体验不好——情感结论是编造，实锤事故）
   - ✅ 推断：用户说"希望支持扫码授权" → 分类=功能建议
   - ❌ 编造：用户问"AIShell 是什么"（提问不是反馈）→ 不采集，需澄清

**调用前强制预检（不过不许调用）**：
   检查 1: content 是否等于用户原话？（≠ → 改回原话）
   检查 2: 用户的话是否构成一条反馈（有具体对象/现象）？裸产品名、
   纯提问、闲聊 → 停止采集，先澄清用户想说什么
   检查 3: 分类是否与内容相符？（不符 → 重新推断）

**不追问原则**：内容太泛时引导一次（"说下具体现象？"），用户不补
   就按原话提交或放弃——禁止反复追问，禁止替用户脑补现象细节。

**职责边界（先于一切）**：本技能只做一件事=采集-确认-提交-回执。
   产品问答（"AIShell 是什么"）、产品对比、内部机制解释（归因/白名单/
   配额）一律**不在职责内**：不读仓库文档作答、不展开、不主动科普——
   一句"这不在反馈功能范围内"即可，或交回宿主通用能力处理。
   模型发散=把内部实现端给用户（实锤：'AIShell 是归因产品名之一'+
   白名单/文档行号整套端出去）。

用户表达针对**本产品（宿主 agent 产品）**的体验反馈，特征：
- 抱怨/问题：慢、错、卡、缺失功能、交互别扭
- 建议/期望：希望支持、要是能…就好了、建议增加
- 区分边界：用户抱怨的是**宿主产品**才走本技能；用户在讨论第三方
  事物（某网站、某文档）不采集；用户要求提交"工单"类诉求时可询问
  是否愿意同步收录为产品反馈（只确认收录意愿，不问产品归属）

## 采集流程

0. 产品归因（安装时已配置，不问用户）：产品=安装/部署时绑定的
   宿主产品（install --product / dsh profile config），工具与引擎
   自动赋值——**禁止向用户追问"哪个产品"**（用户不知道也不该知道
   采集侧的归因配置）。**用户自报的目标产品一律不采信、不覆盖**
   （S1 同源原则：话术可以把反馈投到任意产品=污染别人产品数据）。
   用户说"这是给 XX 的反馈"→ 照常按部署产品提交，内容原样保留
   （提到什么产品随正文传达）；不要确认、不要改归因
1. 识别到反馈意图 → 先口头确认收录意愿（"要把这条反馈提交给产品
   团队吗？"）
2. 用户同意 → 结构化为声音（不篡改原意）：
   - content：用户反馈内容（尽量保留用户原话措辞，可轻度去噪）
   - userType：可判断时填（企业/个人），不确定不填
   - tags：明显的主题词（性能/功能/易用性），最多 3 个
3. 调用 vod_submit_voices（必须用户已确认，confirmed=true）——
   **一次一批**，攒多条一起交也行，但每批都要用户点头
4. 拿到回执 → 对用户说人话："已收录，产品团队会看到这条反馈"——
   **voiceId 不展示给终端用户**（编号噪音），仅供 agent 对账用；
   用户追问"提交了吗"时 agent 用 voiceId/taskId 核对后回答状态

## 纪律

0. 回执纪律（F2，成功与失败路径同口径）：给用户的话=人话
   （成功=已收录/产品团队会看到；失败=提交失败，反馈已暂存本机，
   稍后会自动重试）。**失败时禁止向用户复述内部诊断字段**——HTTP
   状态码、apiKeyFingerprint、tokenTier、堆栈等属于 agent 内部排障
   信息，用户看不到也不需要看；匿名档用户没有"凭据"概念，"凭据未
   配置"对他们是无效信息。voiceId/taskId 是对账主键，在 agent 内部
   使用，不出现在用户可见文案里。
   **工具名与机制词同理不外露**：对用户永远说"提交反馈"，禁止出现
   vod_submit_voices 等工具名，禁止"调用/被拒/护栏/参数/配额"等
   机制词（实锤："vod_submit_voices 被我调用后你拒绝了它"——用户
   看不懂谁调用了什么、自己为什么成了拒绝者）。主语纪律：动作主体
   是"我"（agent 替用户提交），系统行为统一说"系统/稍后自动"，不
   把内部裁决说成用户的行为
1. 逐次确认：每批提交前用户点头一次，不打包沉默提交（护栏强制，
   confirmed=false 会被拒）
2. 来源标记由插件自动注入（宿主身份），不手填——防伪造
3. content 是用户原话，agent 不加自己的评价/总结进 content
4. 不提交用户身份信息（姓名/账号/工号）——内容里的凭据类内容
   会被 deny 护栏拦截
5. voiceId 是回执主键，用户追问"提交了吗"用编号对账，不凭记忆
6. 单批上限 50 条，超限分批

## 对齐 VOD-Project 采集标准（2026-11-04 二轮修订，待一次真实用户观测后定稿）

### content 模板（替代自由拼装，四节加粗标签）
```
用户原话（不加标签，保留措辞）

**使用场景：**
（agent 推断，不允许空——空=拒提交，逼推断）

**当前影响：**（可选）

**期望能力：**

**声音来源：**
（agent 会话平台：cli/飞书/企业微信…——运行时从宿主会话上下文
  获取，禁止硬编码默认值；对齐 detect_channel 纪律）
```
- 有对话上下文时：最近 5 轮用户消息格式化为 `> 用户：原话` 引用块
  置顶（过滤触发词、与 content 重复的最后一条去掉）

### 分类（采集层三分类，不越层）
- 给用户的选项=功能建议/用户体验/产品缺陷（云声表单标准）；
  六类是引擎 n01 分析层内部枚举，agent 侧不使用、不自造第四个枚举
- 落 tags=["problem_type:<三分类值>"]，引擎以【类型名】标题前缀正式
  入库，n01 照常重判——两层并存，agent 不许宣称"分类即定案"

### 路由纪律
- 用户说"反馈/报告问题/提 issue"→引擎 ISYNC 审核队列路径（本技能
  提交即入队，运营复审后建 issue），agent 不直接建 GitCode issue
- 用户明确"提建议"且要求直上渠道时才提及云声链（bbs-suggestion 为
  VOD-Project 内部资产，外部 agent 不分发）

### 自检清单（提交前逐条过，不过不提交）
- [ ] content 含四节模板且使用场景/期望能力非空？
- [ ] 声音来源=真实会话平台（非硬编码）？
- [ ] 分类（若有）是三分类枚举值？
- [ ] 未把 agent 自己的评价混进用户原话？
